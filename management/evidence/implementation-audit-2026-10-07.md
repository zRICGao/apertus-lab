## 3. 当前已经实现到什么程度

### 3.1 固定用例实验链：已具备真实落地证据

`live_contracts.py`、`live_store.py`、`live_transport.py`、`live.py`、`reproduce.py`构成完整的固定用例链：

- 固定CSCS Apertus v1.5 70B目标，明确输入、输出、调用数和时限；不含金额预算或精确定价门槛。
- 事务式请求预留、进程锁、探索/确认分开、重复阶段拒绝、异常停止和中断记录。
- 保存原始响应字节、解析结果、usage与缺失标记、响应模型和结束原因、时间及哈希。
- 区分pass/fail/inconclusive/error，服务问题不会直接计为模型问题。
- 冻结规格和代码清单，独立重跑发出新请求；人工审核入口与正式字段导出已存在。
- 开发版新增成对并行派发，离线测试通过；冻结发布包仍为串行，真实并行调用未验收。

最新Make入口默认自动生成实验ID，因此每次`make run`是一个新实验，并非恢复旧运行。单阶段额度和重复ID保护仍有效，但**它不是跨启动、跨目录或账户级总额度限制**。这是已记录的操作语义，不应再沿用早期“重复make绝不再发请求”的说明。

### 3.2 BASIC 自动探索：实现完整的管理流程，研究有效性未验证

`basic_contracts.py`、`basic_store.py`、`basic.py`、`basic_cli.py`实现了：模板生成、主题种子优先、三种观察路径、有限措辞扩展、父子关系、文本去重、全角色调用计数、复测预留、暂停/恢复/取消、人工支持/否决/复测/归并及候选包导出。

这是真实代码，不应描述为“只有Planner配置”。但也不能称为成熟的自动红队发现系统：

- 默认主题仍是`topic-1`至`topic-5`，不是已定义的领域研究问题。
- 当前持久验收使用确定性模拟器；未见BASIC live生成模板和实际探索的运行证据。
- 变体只改变probe措辞，语义等价性标为unverified；没有多语言等价性审核或系统化攻击维度搜索。
- 同一Apertus承担生成、观察与受测，独立会话隔离了上下文，但不会消除同模型的共同偏差。
- exact判定的expected也可能来自模型，结构校验不证明其正确；model判定是辅助观察，不能替代外部事实依据。
- `basic.py:374`人工支持后的状态仍为`human_supported_placeholder`；`official_export_allowed=False`是明确保护边界。

### 3.3 工作台与知识层：有可用的局部集成

本地工作台已能只读展示MVP运行、逐条输入/回答/判定、结论和Wiki引用状态。`local_lab.py:21`使用只读SQLite连接；同步到BreachWeave提取的Memory与Wiki文件有幂等和人工修改保护。

### 3.4 发布和版本：能运行，但还不是完整可交付基线

## 5. 可改进的工程与研究方向

### P1：先闭合会阻断成果的环节

1. **将一个有依据的候选转成正式实验。** 保留来源、人工确认expected/事实依据，冻结用例与规则，再独立重跑。不要解除placeholder限制来缩短路径。
2. **建立有实际影响的问题定义。** 当前BLUE示例适合连通性和链路测试，不能代表红队覆盖。对Track 1A，需要明确任务场景、受影响对象、何种行为构成失败及为什么有影响。
3. **明确最终赛道和交付仓库。** 主文档写1A，另有独立2B仓库；应由项目决策统一目标、可见性、演示和验收，不能让目录复制代替赛道选择。
4. **完成版本和最终包验收。** 固定可检出提交与发布源清单，执行干净环境重跑；组装整个提交而不是只验证一个导出函数。

### P2：提高可靠性与日常使用效率

- **拆分运行指纹与全包清单。** `live_contracts.py:90`把目录全部Python文件纳入runner hash，`basic.py:250`在继续任务前比较它。即使只改Wiki或CLI展示，也会让旧campaign不能继续。保留严格冻结原则，但分开transport/evaluator/policy指纹与非行为代码清单，并提供明确兼容迁移机制。
- **控制BASIC存储增长。** `basic_store.py:59`每个状态变更追加完整状态快照。当前66调用、200条history，SQLite已约13.09 MB，既有导出约14.24 MB。扩大任务后有显著增长风险；建议事件记录＋周期checkpoint，响应文本单独保存和引用。不能直接按当前体积断言具体极限，但应做容量基准。
- **把模型自评与证据判定分开显示。** 展示“模型建议”“规则观察”“人工结论”三种来源；对同模型生成/观察明确偏差限制。没有必要仅为表面独立立即增加第二个模型，但不能把新会话当作独立事实核验。
- **统一配置语义。** Make加载本地`.env`，BASIC CLI主要读取当前环境；两个入口的可用性可能不同。提供只读预检，显示配置来源和是否满足条件，不显示key，不将自动读取配置误作调用授权。
- **改善状态文档。** STATUS中多个“最新”及历史“下一步”并存；ARCHITECTURE/PROJECT_OUTLINE仍含被后续BASIC指令覆盖的章节。增加唯一当前摘要，历史移入WORKLOG，任务表同步实际G3与重跑进度。
- **完整Wiki先做小闭环验收。** 先验证现有页面读取、一次人工修改、来源查看、同步不覆盖及引用检查。大型图谱、自主维护、多Agent UI仍应后置。

## 6. 与题目要求的预期偏差

### 6.1 主目标 Track 1A

官方要求以Apertus问题为成果，每个问题独立文件，最多五项；运行需Docker和make入口，报告PDF不超过六页，并有特定的私有提交和许可要求。问题评分关注影响严重性、影响范围、新颖性、有效性/复现；基础设施本身不替代这些证据。[赛道说明](https://raw.githubusercontent.com/HackApertus/project-template/main/track_1a/README.md)

| 维度 | 偏差度 | 判断 |
|---|---|---|
| 模型与输入范围 | 低 | 70B＋文本符合范围；不必为了完整性加入8B或多模态 |
| 请求、证据和独立重跑 | 低至中 | 当前机器固定示例已真实运行；新BASIC/并行路径仍仅离线验证 |
| 真实问题及研究有效性 | 高 | 36次真实请求均支持预期行为；没有可确认的问题，也无实际影响/新颖性论证 |
| 自动发现能力与描述 | 中至高 | 有管理流程，缺真实探索质量证据；若称“自主漏洞发现系统”则超过已验证能力 |
| 正式数据与报告 | 高 | 正式finding及PDF均缺；报告是实现草稿 |
| 干净交付与版本 | 中至高 | 本机Docker可用，但根无提交基线、干净检出及全包验收未闭合 |
| Wiki/工作台投入与评分收益 | 中 | 有助研究和报告；过度优先于有效问题会偏离1A评分重心 |

根模板还要求规定的LLM环境变量及data大小限制；当前入口和示例大小符合相应方向，但需对最终包整体复验。[根模板](https://raw.githubusercontent.com/HackApertus/project-template/main/README.md)

综合偏差：**技术方法方向基本一致，最终成果与评分证据存在较高偏差。** 不给单一“完成百分比”，因为目前没有已确认问题，代码完成量无法按比例折算成参赛完成度。

### 6.2 新发现的 Track 2B 基线：不能视为已经转赛道成功

`submission/team-track-2b`是独立Git仓库，当前提交`694f98e`（Add Track 2B team baseline），本轮状态干净。其Docker默认命令仅执行`run-mock`，Make没有接入LLM环境透传或持久化输出，报告仍为官方占位模板。没有证据表明该包已完成Apertus驱动的产品演示。

2B针对使用Apertus的工作原型，要求声明符合指定部署架构、公开仓库、六页以内报告和两分钟以内演示视频。它与1A私有提交规则不同。[2B官方说明](https://raw.githubusercontent.com/HackApertus/project-template/main/track_2b/README.md)

## 7. 项目落地程度

使用以下分级，避免把代码存在等同于可交付：L0=设计，L1=有代码，L2=离线/局部验证，L3=真实环境流程验证，L4=干净环境和最终验收完成。这不是官方评分。

| 能力 | 当前级别 | 依据与限制 |
|---|---|---|
| 固定示例runner＋证据＋replay | L3 | 两组真实流程完成；单一示例，不代表任意问题 |
| BASIC自动探索与人工队列 | L2 | 离线完整执行与专项测试；无真实BASIC运行证据 |
| 成对并行调度 | L2 | 并发/取消/错误测试；无真实并行CSCS验收 |
| 本地只读工作台＋派生同步 | L3（局部） | 能读取真实账本；已有浏览器记录，本轮HTTP集成测试通过；BASIC未接入 |
| 完整Wiki研究应用 | L1–L2 | 源码/依赖存在，候选文件可用，完整API/Web及审核闭环未验收 |
| 人工Registry和单finding导出 | L2 | 代码与fixture正负例通过；真实review为0 |
| Track 1A最终成果 | 未达到提交验收 | 无真实finding和PDF，G0/G4/G5/G6/G7仍有缺口 |
| Track 2B副本 | L1–L2 | 有基线提交与mock入口，未展示完整真实产品 |
